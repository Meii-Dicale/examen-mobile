≈ 50 s. SDK 57 et pas 58 : le 58 venait de sortir et Expo Go ne le supportait pas encore. SQLite plutôt qu’AsyncStorage : utilisateurs, événements, participations et photos sont liés ; SQLite garantit l’e-mail unique, une seule participation par personne, la suppression en cascade, et trie par date. ≈ 50 s. Le flux : l’écran appelle un hook, le hook appelle un service, le service parle à SQLite ou à l’API. Règle reprise de mon projet YouAreTheHero. useFocusQuery gère chargement, erreur et annulation pour tous les hooks de lecture ; il utilise useFocusEffect, donc pas besoin d’un état global pour rafraîchir. Piège : la requête passée doit être stable (useCallback), sinon elle tourne en boucle. État global limité à trois Contexts : Auth, Theme, Location.

La base de données

Quatre tables, et la base garantit les règles

users

email UNIQUE NOCASE · password_hash · salt

events

date ISO · latitude · longitude · created_by

participations

PRIMARY KEY (user_id, event_id)

event_photos

event_id · user_id · uri (chemin relatif)

Migrations versionnées

PRAGMA user_version, une transaction par migration : jamais une base à moitié migrée.

Intégrité

foreign_keys activé à chaque ouverture, ON DELETE CASCADE, pas de double participation.

Requêtes paramétrées

Les valeurs passent par « ? », jamais concaténées : pas d’injection SQL.

EventEase · Soutenance CDA

6 / 13

≈ 50 s. user_version vaut 0 sur une base neuve : on ne joue que les migrations manquantes, et on n’en modifie jamais une existante. SQLite ignore les clés étrangères par défaut, d’où PRAGMA foreign_keys = ON à chaque ouverture, sinon la cascade ne ferait rien. Dates en ISO 8601 : l’ordre alphabétique est l’ordre chronologique, ORDER BY date suffit, avec un index. Une seule requête pour la liste : COUNT des participants et LEFT JOIN sur ma participation, pas de problème N+1. Contraintes testées avec sqlite3.

La sécurité

Ne jamais faire confiance à l’interface seule

Mots de passe

SHA-256 avec un sel aléatoire par compte. Jamais stockés en clair.

Session

Seul l’id, dans SecureStore. Stack.Protected bloque l’app sans session.

Droits vérifiés en SQL

UPDATE … WHERE id = ? AND created_by = ?

Masquer un bouton ne protège pas d’un lien direct.

Clé d’API

Dans .env, ignoré par git. Mais EXPO_PUBLIC_ est intégré à l’app : en production, un serveur garderait la clé.

EventEase · Soutenance CDA

7 / 13

≈ 1 min. Le sel rend inutiles les rainbow tables. Pourquoi pas bcrypt ou argon2 : les versions natives ne marchent pas dans Expo Go, bcryptjs fige l’interface environ 1 s ; sur un vrai serveur je hacherais avec argon2. Même message pour e-mail inconnu et mauvais mot de passe (pas d’énumération des comptes). Le User de l’app ne contient jamais le hash. Droits : vérifiés deux fois, bouton masqué ET clause SQL ; testé avec sqlite3, changes = 0. Même principe pour les photos : INSERT … SELECT qui exige une participation à un événement passé, DELETE … AND user_id = ?.

Un bug raconté

L’écran blanc, sans aucune erreur

1 · Symptôme

Écran blanc au démarrage, au hasard.

2 · Démarche

Un console.log à chaque étape : polices, base, splash.

3 · Cause

SQLiteProvider est en React.memo : l’état des polices ne descendait pas.

4 · Correction

useFonts déplacé sous le provider.

L’état doit vivre au plus près de là où il est utilisé.

EventEase · Soutenance CDA

10 / 13

≈ 50 s. Indice décisif : les logs disaient « polices chargées : true », mais l’enfant recevait toujours fontsReady = false. J’ai lu le code source d’expo-sqlite : SQLiteProvider est mémoïsé avec une comparaison qui ignore ses enfants. Leçon : memo évite des rendus inutiles mais peut bloquer une mise à jour attendue. Autre bug possible si on me demande : « Zzzzz » à 1 611 km, le géocodeur renvoie toujours le lieu le plus ressemblant, donc le formulaire affiche maintenant « Lieu reconnu : Ville, Pays ».
